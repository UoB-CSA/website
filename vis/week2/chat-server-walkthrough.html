From empty functions to a working chat server

Seven steps that build the Go chat system from the skeleton: a client that listens and types at the same time, and a server made of goroutines, two channels and one map of connections. The server diagram is a live simulation. Connect clients, send messages, and watch every value move.

    goroutine
    channel
    shared data (the map)

    The brief

    Many clients talk through one server. The server must listen for new clients, read what each one types, and pass every message to everyone except the sender. The client must type and listen at the same time.

    The client: two jobs at once
    
    
    Reading from the keyboard blocks until you press Enter. Reading from the server blocks until a line arrives. One goroutine can only be stuck in one of those at a time, so the client uses two.

    Accepting connections
    
    
    The server listens on a port. ln.Accept() blocks until someone connects, so a dedicated goroutine, acceptConns, does that forever and passes each new connection through the conns channel to main. Main adds it to the clients map.

    Why a map and an ID counter, not a plain list?
    
      
    Each handleClient goroutine remembers the ID it was started with. That ID must keep pointing at the same client for the whole life of the server. Remove a client and see what happens in each design.
    
      
    
        
    
          
          
        
    
        
        
        
      
    
      
    
        
    
        
    
          
    
          
    
        
    
      
    
    
    
  
    

  
  
    
    
    A goroutine for each client
    
    
    Reading a line from a client blocks until that client types something. If main did the reading, one quiet client would freeze everyone. So each client gets its own handleClient goroutine, and they all send what they read into the same msgs channel.
    
    
    
      
    
        
    
        
    
        
    Tap a marked line.
    
      
    
      
    
        
    
      
    
    
    
    
    Both channels are unbuffered. A sender waits until main is back at its select, and the diagram shows waiting senders as dots in the pipe. Send from two clients quickly to see them queue up.
    
  
    

  
  
    
    
    Broadcasting from the select loop
    
    
    Main's select waits for whichever channel is ready, then runs that case to completion. For a message, it walks the clients map and writes to every connection except the sender's.
    
    
    
      
    
        
    
          
    
          
    
          
    Tap a marked line.
    
        
    
        
    
          
    Who touches what?
    
          
    
          
    Only main reads or writes clients and n. New connections and messages reach it through channels, one case at a time, so no lock is needed.
    
        
    
      
    
      
    
        
    
      
    
    
    
    
    
      
    
        What if handleClient also added itself to the map?
        
    Then two goroutines could write to the map while main is ranging over it. Go's runtime detects this and crashes the program with fatal error: concurrent map writes (or reads and writes). You'd need a sync.Mutex around every access. Funnelling everything through channels into one goroutine avoids the problem entirely.
    
      
    
      
    
        Why does the delivery order change from message to message?
        
    Ranging over a Go map visits entries in a deliberately randomised order. The simulation shuffles the visit order for each message to show this. It doesn't matter for a chat room, but you can't rely on it.

    What the disconnect shows
    
        
    When a client quits, its handleClient gets an error from ReadString and exits. The skeleton solution never tells main, so the dead connection stays in the map and every later broadcast writes to it. The write error is ignored, so nothing breaks, but the entry is never cleaned up. The extension box shows one fix: have the exiting goroutine report to main, which deletes the entry.

    Gotchas
    
        
    
          The message is used as a format string
          
    Both programs call fmt.Fprintf(conn, text), so any % in a chat message is treated as a formatting verb. Try it:
    
          
          
    Fprintf(conn, text) sends:
    
          
    
          
    Fprint(conn, text) sends:
    
          
    
          
    Use fmt.Fprint or io.WriteString when the text isn't a format.
    
        
    
        
    
          Closed clients stay in the map
          
    Step 6 shows it. Every broadcast keeps writing to dead connections, and the map grows for the life of the server. Fix it by telling main when a handleClient exits and calling delete(clients, id).
    
        
    
        
    
          The client spins when the server goes away
          
    read ignores the error from ReadString. After the server closes the connection, every call returns immediately with an error and an empty string, so the loop prints :: as fast as it can.
    
          
    
          
    Check err and return when it isn't nil.
    
        
    
        
    
          Errors that are only printed
          
    handleError just prints. If net.Listen fails, ln is nil and acceptConns then crashes on the first Accept. On the client, if net.Dial fails, conn is nil and the first read crashes. Exiting on a startup error is usually better.
    
        
    
        
    
          One slow client can stall everyone
          
    All the writes happen inside main's select case. A client whose connection stops accepting data would block that write and, with it, every other client's messages. A common fix is a writer goroutine and a channel per client.
    
        
    
        
    
          Small things
          
    The /quit check compares with "/quit\n", which won't match on a terminal that sends \r\n. Messages keep their trailing newline, which is why the client's Println leaves a blank line. net.Conn is already an interface, so passing *net.Conn is unnecessary.
