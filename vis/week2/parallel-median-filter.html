From panic("TODO") to a parallel median filter

Seven short steps that build the Go solution from the question: cut the image into strips, wrap the filter in a worker, give every worker its own channel, then stitch the strips back together. Every picture here is computed live with the same five-by-five median filter as the Go code.

    Check your understanding
    
        
    
          Why a slice of channels rather than one channel?
          
    With one channel, strips arrive in finish order, so the rebuilt image comes out shuffled (try it in steps 4 and 5). A slice lets main receive from out[0], then out[1], and so on, which fixes the order in the code, not by timing.
    
        
    
        
    
          Why doesn't immutableData need a mutex?
          
    Every worker only reads it, and nothing writes to it after it is built. Concurrent reads of data nobody modifies are safe. Each worker writes only to its own filteredMatrix.
    
        
    
        
    
          What goes wrong if the height isn't divisible by the thread count?
          
    height / threads rounds down, so the last few rows belong to no strip. newPixelData ends up shorter than height rows, and imout.Pix is too short for the image bounds. Pick 3 threads on the left to see a missing row. A fix is to give the last worker height as its endY.
    
        
    
        
    
          Could main just wait with a sync.WaitGroup?
          
    It could wait, but the workers would still need somewhere to put their results. Channels hand over the data and the synchronisation in one step.
    
        
    
        
    
          An aside on the median itself
          
    The provided code picks index (5*5+1)/2 = 13 from the 25 sorted values. The exact middle is index 12, so it's slightly off. It doesn't affect the parallel work, and the live demos here copy it faithfully.
