99 bottles of beer, passed around a ring over RPC

A few processes sit in a ring. Each one knows only its neighbour. A single value, the number of bottles, is handed from process to process by remote procedure call, and each one sings a verse when it gets it. Six steps build the solution, with a live ring you can start, break and watch.

    The brief: a ring of processes

    Run the same program several times, each in its own terminal. Every copy listens on its own port and is told the address of the next copy. One copy is also told how many bottles to start with. That copy sings the first verse and sends the count on. Each receiver sings one verse and passes it along, until the count reaches zero.

    Exposing a method over RPC
    
    
    Go's net/rpc lets one process call a method on another as if it were local. The receiving process registers a type, listens on a port, and accepts connections. Each call arrives as a method call on that type.
    
    
    
      
    
        
    
        
    
        
    Tap a marked line.
    
      
    
      
    
        
    What counts as an RPC method?
    
        
    Pick a signature. net/rpc only exposes methods that follow its rules.
    
        
    
        
    
        
    The rules: the method and its type are exported, it takes two arguments of exported (or built-in) types, the second is a pointer, and it returns error.

The call is named by the type and method, "BottlesOfBeer.Round", because that is how it was registered.

      Watch the token go round
      
    
      When Round is called, it sleeps a second, sings the verse, and, if there are bottles left, calls Round on the next process with one fewer. At zero it sings the last verse and stops.

      Go or Call?
      
        
      The solution uses Go, so each Round returns right after it hands the token on. Tick the box below to switch to Call and see the difference.
      
        
        
          
      • With Go, no handler waits for anything, and the replies that come back are thrown away.
        • 
          
      • With Call, each handler stays blocked until the whole rest of the round has finished. The open calls pile up around the ring, then unwind in reverse at the end.
        • 
        
      
        
      Press Start ring. It starts C, then B, then A, with A launching the round.
      
      
      
    
      
    
      
  
      

  
  
      
    
      Starting the round, and breaking it
      
    
      The starter sings the first verse itself, then sends the token on in a goroutine and starts serving. Because errors from dialing and calling are ignored, a ring with a missing or dead member doesn't fail loudly. See for yourself.

      Experiments
      
        
        
          
      • Wrong order. Start only A. It sings, tries to dial B, and crashes with a nil pointer panic.
        • 
          
      • A node missing. Start A and B but not C. B crashes when it tries to pass the token to C.
        • 
          
      • Kill a node mid-round. Run the whole ring, then press Stop on B during the song. Nothing complains. The ring just goes quiet.
        • 
          
      • Restart it. Start B again. The song doesn't resume: nobody holds the token, and A's old connection to B is dead.
        • 
        
      
        
      Set the speed to Fast to get through verses quickly. The starter's bottle count is on A's card.

      Gotchas
      
        
      
          The verses run together
          
      The format strings for the verse end in "pass it around..." with no \n, so the next verse starts on the same line. The terminals in step 4 show it. Add a newline to the format string if you want one verse per pair of lines.
      
        
      
        
      
          Every error is thrown away
          
      rpc.Register, net.Listen, rpc.Dial and the result of Go all have errors that are ignored. A failed Dial leaves nextround nil, which panics on the next line. A broken connection makes Go fail quietly. Checking those errors and printing them would make the failures in step 5 obvious.
      
        
      
        
      
          Shared globals and goroutines
          
      initialised and nextround are plain globals. The starter calls PassItAround from one goroutine, and each incoming Round runs in yet another. Only one token is ever in flight, so in practice they don't collide, but the language doesn't guarantee that. go run -race or a mutex would make it safe.
      
        
      
        
      
          Why go PassItAround in main?
          
      So main goes straight on to rpc.Accept and starts serving, while the dial and the first call happen in the background. Calling it directly would also work here, since Go doesn't wait for the reply.
      
        
      
        
      
          The processes never exit
          
      rpc.Accept never returns, so after the last verse every process keeps listening until you press Ctrl-C. The token simply stops at zero: that process sings the final verse and doesn't pass it on.
      
        
      
        
      
          Counting verses
          
      The starter sings n, then the token carries n-1, and so on down to 0, so a ring started with -n 99 sings 100 verses, the last of them "No more bottles".
